## 1. Frontend: pages, states, UI behaviour

### Takeaway
Single-page React 19 + Vite 8 app, two "pages" (Home, Authors) switched by useState, no router. Home = 30/70 two-panel grid: dark-green upload panel left, cream result/tutorial panel right. Input is paste (Ctrl+V) or Browse; drag-and-drop is NOT implemented despite README claim. Loading UX is only a button label + a 40s note. Failed scans silently show nothing. Result UI shows 4-decimal raw probabilities, a table of all classes, 3 variant cards with Google Images links, and a templated summary sentence.

## 2. Backend / ML

### Takeaway
Pipeline: Grounding DINO (zero-shot "watch. wristwatch.") crop -> OpenCV Canny+PCA bracelet rotation -> contour dial crop -> EfficientNet-B0 family classifier (14 classes) -> zero-shot CLIP (ViT-B/16) over hand-written text prompts of the predicted family's variants -> top-3 variants with reference IDs. There is no embedding/nearest-neighbour retrieval against images; variant "match" is text-prompt zero-shot only. No evaluation numbers are stored in the repo. No confidence threshold or non-Rolex rejection on the classifier.

### Cited Findings
- Classes: 14 in class_mapping.json (data/processed/class_mapping.json): airking, cellini, datejust, daytona, explorer, gmt_master, milgauss, oyster_perpetual, oysterquartz, president, sea_dweller, submariner, turn_o_graph, yacht_master. README says "15 Rolex families" (README.md L31, L44, L106) - wrong/stale; no-watch dict in main.py L202-218 lists 15 incl. "date". data/duplicates and data/raw_incoming also contain `datejust41` folder, which is not in the mapping. Note "President" (Day-Date) is a family; "Cellini" is a dress family.
- Model: torchvision efficientnet_b0, classifier[1] replaced with Linear(num_classes) (src/training/models.py), ImageNet-pretrained init. Checkpoint models/rolex_classifier_model.pt = 16.4 MB (16,401,505 B), dated Aug 15; contains state_dict, class_names, image_size, model_name (train.py L9-24).
- Training: AdamW lr 1e-4, batch 16, 5 epochs default, CrossEntropy, CPU device hard-coded (train.py L77-85, L106-108); best val-accuracy checkpoint saved. README says ~5 hours for training (README.md L181). No class weighting, no sampler, no LR schedule, no early stopping, no seed.
- Augmentation (src/training/dataset.py L17-45 area): RandomResizedCrop 224 (scale 0.75-1.1, ratio 0.85-1.5), RandomRotation 55 deg, RandomPerspective 0.25 p0.35, ColorJitter, RandomErasing p0.2. No horizontal flip. Inference transform: Resize((224,224)) (squashes aspect ratio, not centre-crop), ToTensor, ImageNet mean/std normalise (dataset.py build_transforms train=False).
- Training data source: ONE source only - swisswatchexpo.com (manifest data/manifests/images.csv, 34,371 rows, all source_name=swisswatchexpo; status: 25,985 downloaded, 8,383 duplicate, 3 invalid). Images are retailer product photos (e.g. 500x500 CDN thumbnails, "_sm.jpg") with white/studio backgrounds; listing_title captions are present. Scrapers in src/collection/ (sources.py, collect_images.py, build_dataset.py, remove_dup_images.py using imagehash/sha256).
- Processed split counts (counted from data/processed/{train,val,test}): train = airking 947, cellini 1014, datejust 6457, daytona 667, explorer 800, gmt_master 840, milgauss 136, oyster_perpetual 1169, oysterquartz 146, president 2173, sea_dweller 355, submariner 1397, turn_o_graph 379, yacht_master 867 (total 17,347). val ~ 3,917 (e.g. datejust 1383, milgauss 29), test ~ 3,931 (datejust 1385, milgauss 30). Split ~70/15/15. Strong imbalance: datejust 6,457 vs milgauss 136 (about 47:1) and oysterquartz 146; datejust ~37% of train. Whether test set is image-level split (possible near-duplicate leakage across same listing/watch) is not documented - not verified.
- Domain gap: training = clean retailer shots; user uploads = wrist shots, lighting, angles. Inference-time crop pipeline is applied to user photos but training images in data/processed were NOT passed through the same Grounding DINO/PCA/dial crop (no such step in src/collection or training; dataset.py uses plain ImageFolder). So train/inference preprocessing mismatch (training sees full product photos with augmentation; inference sees tight dial crop). Inferred from code, not measured.
- Evaluation: src/training/evaluate.py computes only test loss + overall accuracy on CPU (L41, L67-88). No confusion matrix, per-class precision/recall, top-k, calibration, or CLIP/variant-level evaluation. No saved results/metrics files anywhere; README has no accuracy figure (grep accuracy/confusion/top-k in README/docs/tests: only README mentions limitations, docs plans, tests/identify/test_clip_matcher.py). scikit-learn and matplotlib are in requirements.txt but unused for metrics in src/training. Tests directory covers collection, detection, identify, training, api (tests/**), unit-level; no model quality tests.
- Inference preprocessing (src/detection/watch_cropper.py; called by main.py L197):
  1. Grounding DINO base (IDEA-Research/grounding-dino-base), prompt "watch. wristwatch.", BOX_THRESHOLD 0.30, TEXT_THRESHOLD 0.25 (L10-13). Highest-score box only (L390). Box padded 12% (L14, expand_box); rejected if padded box < 2% of image area (L15, is_valid_box) -> falls back to the full image (crop_from_box L74-81), pipeline continues.
  2. Bracelet alignment: Gaussian blur + Canny(50,150), mask out centre 42% of crop (L17, L96-106), PCA on remaining edge points; require >=120 edge px and axis confidence (eigen ratio) >=1.8; skip if within 12 degrees of vertical; else `image.rotate(90 - angle, expand=True)` (L262-313). Rotate fills with black corners (PIL default, expand=True). Note: PCA axis sign ambiguity - could rotate 180 deg (watch upside down) since angle only mod 180; not handled. (Inferred from code; training augmentation RandomRotation 55 only, so upside-down input not covered.)
  3. Dial crop: search central 78% region, Canny, external contours, bounding rect filters (area 6-70% of image, aspect 0.65-1.55, centre within 0.28 of diagonal), weighted score 0.35 centre + 0.30 roundness + 0.20 size + 0.15 fill, min score 0.45, pad 40% (L22-29, L146-260). Bugs: `y2 = y1 + width` instead of height (L181) so box height wrong for non-square contours; info dict key typo "jarea_ratio" (L243); box compared to full-image area although search region is a crop; no minimum-circle fit/ellipse despite "dial" claim; falls back silently to aligned crop if no confident dial.
  4. Final image resized to 224x224 by the classifier transform (squash). CLIP processor resizes to 224 too (CLIP pipeline default).
  No background removal, no segmentation mask, no super-resolution, no image-quality gating (blur/size), no EXIF orientation handling (decode_image uses `Image.open(...).convert('RGB')` without `ImageOps.exif_transpose`, main.py L62-69) - phone photos with EXIF rotation may be fed rotated. Unvalidated assumption; PIL does not auto-apply EXIF.
- Non-Rolex / non-watch rejection: only Grounding DINO "no detection above 0.30" -> "No Watch Detected" (main.py L198-248). The classifier always returns a Rolex family via softmax over 14 classes with no threshold; a non-Rolex watch (Omega etc.) that DINO detects is labelled with some Rolex family at whatever softmax confidence. README acknowledges false positives for non-watch objects (README.md L168-170) but not other brands. Header shows "Confidence xx.xx%" with no low-confidence warning state in UI.
- Variant matching (stage 2): src/identify/clip_matcher.py. Zero-shot `pipeline("zero-shot-image-classification", model="openai/clip-vit-base-patch16")` (L11, L22-28), fp16 on CUDA. Candidate labels = `clip_text` strings from src/identify/rolex_variants.json for the predicted family only. 95 variants across 14 families: airking 4, cellini 11, datejust 6, daytona 9, explorer 5, gmt_master 10, milgauss 3, oyster_perpetual 9, oysterquartz 2, president 6, sea_dweller 5, submariner 8, turn_o_graph 5, yacht_master 12. Each variant = id, display_name, reference_examples (list of ref numbers), clip_text (long natural-language description). Top-3 returned (rank_variants top_k=3). Scores are the pipeline's softmax over those prompts (relative, sum to 1 within family). Because CLIP text encoder truncates at 77 tokens, long prompts (many exceed 77 tokens) are truncated - inferred, not verified per-entry.
  - No image-embedding nearest neighbour, no reference image gallery, no FAISS/vector index, no fine-tuning of CLIP. Variant accuracy is not evaluated anywhere.
  - Status logic (L83-96): if top score < 0.35 or (top - second) < 0.08 -> status "closest_known_matches" + note "The exact variant may not be in the catalog; these are the closest known matches"; else "matched_known_variant" with note "The top result is the strongest match ... not a guaranteed exact reference". Frontend ignores `variant_status` (always shows MatchNotice titled "Closest known matches" even for the confident case).
  - Catalog typo: id "airking_classing_fluted" (rolex_variants.json). For families with few variants (oysterquartz 2, milgauss 3) the top-3 is trivial.
  - Reference IDs shown are lists of examples per variant (e.g. Air-King Modern: 126900, 116900), not a single resolved reference; user is pushed to Google for confirmation.
- API flow (src/api/main.py): POST /predict (L193-255) -> decode -> crop_watch_stages (Grounding DINO + CV) -> predict_image (EfficientNet softmax, then rank_variants) -> adds crop_info, processed_image_path, steps. `save_processed_image` deletes all files in output_image/ then writes one JPEG q95 (L179-188): not safe under concurrency, writes disk per request; output_image/watch_20260710_07182.jpg is tracked in git (user-photo privacy concern if any real upload committed). GET /health (L258). CORS allow origins vercel.app + onrender.com. FastAPI also mounts front_end/dist if present (L266-268).
- Inference is sequential per request with 3 models: DINO base (~233M params, as per its public card, not in repo), EfficientNet-B0 (5.3M), CLIP B/16 (~150M); `get_detector` in watch_cropper uses `lru_cache`.

### Inferences
- Variant stage is the weakest link for credibility: zero-shot text prompts for fine-grained reference differences (e.g. 116610LN vs 126610LN) have no measured accuracy, yet the UI presents "Match Score" percentages and reference IDs.
- Classifier confidence is likely over-confident (softmax, no calibration, no OOD), and the UI shows it to 2 dp / 4 dp.
- Single-source retailer dataset + class imbalance (datejust 37%, milgauss <1%) + no per-class metrics means accuracy claims on minority families are unknown.

### Gaps
- No test accuracy number, confusion matrix, or latency benchmark is stored in repo; could only be produced by running evaluate.py (not run here).
- Whether Render or Modal is the front-door for the website static files was not verified beyond the fetched HTML.

## 3. Infra: Modal vs Render, cold start

### Takeaway
Render hosts the static React bundle (always-on/ free tier, may itself sleep). All ML runs on Modal (GPU serverless, scale to zero). Cold start (README ~40s) = Modal container allocation + image pull + Python imports + loading three models onto GPU. Current mitigation: build-time HF weight bake, a health-ping on page load, 1200s scaledown, and a UI note. No keep_warm/min_containers, no snapshotting, no ONNX/quantisation.

### Cited Findings
- modal_app.py (86 lines): app "rolex-watch-recognizer"; `@app.cls` with `gpu="L4"` committed -> working-tree edit to `gpu=["L4","T4","A10G"]` (fallback list; git diff shows only that one-line change at L68), `min_containers=0`, `max_containers=1`, `scaledown_window=1200` (20 min), `timeout=180`, `startup_timeout=180`, `@modal.concurrent(max_inputs=1)` (L66-77). `@modal.enter()` `load_models` calls `warm_models()` which loads classifier, Grounding DINO, CLIP (src/inference/warmup.py; L79-82). ASGI app wraps FastAPI (L84-87).
- git diff (uncommitted, only modified file): `-    gpu = "L4",` / `+    gpu = ["L4", "T4", "A10G"],` in modal_app.py. Intent (inferred): widen GPU availability pool to cut container allocation wait; T4/A10G are alternate types. Last commit 094bbea 2026-11-15 "minor updates".
- README says scaledown_window = 180s / "3 minutes" (README.md L35, L125) but code is 1200s (20 min); README stale. Also README says 'Hosted on Modal (NVIDIA L4 GPU)'.
- Image build: debian_slim py3.11, apt libgl1/libglib2.0-0, pip install requirements.txt, `run_function(download_huggingface_models, secrets=[hf_secret])` bakes grounding-dino-base + CLIP into image layers (L11-42); src/, models/, class_mapping.json copied in (copy=True). Env MODEL_DEVICE=cuda, HF_HOME=/root/.cache/huggingface (L58-62). Note CLIP pre-bake loads on device=-1 (CPU) at build.
- 40s cold-start composition (README L176-178 states "roughly 40 seconds to spin up the container and load models into GPU memory"; no per-phase timing exists in repo): (a) Modal GPU container scheduling/allocation + image layer pull (large: torch + transformers + weights); (b) Python import of torch/transformers/cv2; (c) `torch.load` of 16 MB EfficientNet + `from_pretrained` of Grounding DINO base (~0.9 GB fp32 weights, per HF model card - external knowledge, not repo-verified) and CLIP B/16 (~600 MB) from disk to GPU; (d) first CUDA kernel warm-up on first request is NOT done in warm_models (no dummy forward pass). Breakdown is inferred; no instrumentation or logs in repo.
- Other latency characteristics: DINO runs in fp32 (no `torch_dtype=float16` for DINO; CLIP uses fp16 on cuda, clip_matcher.py L27); each request does DINO full-res inference via processor resize, Canny ops on CPU, 3 forward passes, and builds 4 base64 images for `steps` (main.py L138-177) that the front end discards; `max_inputs=1` serialises requests per container and `max_containers=1` caps to one container -> simultaneous users queue and a second user hitting a cold container waits.
- Warm request time observed: /health round trip 0.4s (first) and 0.24s (second) from this machine on 2026-11-15, so the container was warm at fetch time or health is fast; not a /predict timing. /predict latency not measured (would need uploading an image).
- Mitigations present: HF weights baked at build; ping `/health` on page load (App.jsx L21-24) so container starts while user selects an image; `scaledown_window` 20 min; 40s note while scanning. Missing: min_containers=1 / keep_warm (cost), `enable_memory_snapshot` / GPU snapshot (Modal feature, not used), model size reduction (DINO base -> tiny, FP16/bfloat16, ONNX/TensorRT, torch.compile), CPU-only first-pass, progress/status endpoint or warm-state indicator in UI, retry/timeout handling in UI, client-side image downscale before upload, removing `steps` payload from response, request coalescing.
- Render: Dockerfile (15 lines) builds a FastAPI-only image (python:3.11-slim, installs requirements, pre-downloads Grounding DINO only, copies src/models/class_mapping, uvicorn on $PORT default 10000) - it does not copy front_end/ and .dockerignore lists `front-end/dist` (hyphen, wrong folder name vs front_end), so the API's static mount of front_end/dist (main.py L266-268) would not serve the UI from this image. How Render is configured (static site vs docker web service) is not in repo; the live site returns the Vite SPA HTML, and the browser calls Modal directly. CORS allow list includes both Render and Vercel (main.py L29-39); README credits Vercel deployment for frontend; sitemap/robots reference onrender.com. Vite dev proxy forwards /predict to the Modal URL (vite.config.js L7-9).
- Render free-tier sleep: not documented in repo; a static site does not sleep, a free docker web service does (general Render behaviour, not repo-verified). README attributes the ~40s only to Modal.
- requirements.txt: `opencv-python-headless>=4.1010` (odd version spec), `pytest` and scraping libs (bs4, imagehash, pandas, matplotlib, scikit-learn) all installed into the production image -> larger image / slower pull. Unpinned (>=) versions -> non-reproducible builds.

### Inferences
- Biggest cold-start cost is probably model loading of two HF models plus container/GPU scheduling; a memory snapshot (Modal) or smaller detector would be the most direct cuts. Not measured.
- `max_containers=1` + `max_inputs=1` means traffic spikes (e.g. a shared link) will queue.

### Gaps
- No timing logs/benchmarks in repo for any phase; breakdown above cannot be quantified. Render service type unverified. /predict latency not measured.
